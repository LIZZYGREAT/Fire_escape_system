# 一、半自动地图编译与布点编辑器

```text
导入建筑平面图
    ↓
人工或半自动标注墙体、走廊、门、出口、避难点
    ↓
自动提取走廊中心线
    ↓
自动识别路口、转弯、盲端
    ↓
自动生成黑盒候选位置
    ↓
人工拖动、增加、删除和锁定
    ↓
自动检查覆盖、视线、连通、路径链和冗余
    ↓
导出标准地图包
```

这是“算法自动推荐 + 工程人员最终确认”的模式，安全性和可控性都更高。

---

# 二、可以分成三个实现等级

## 1. 基础人工编辑器

先完成最核心功能：

* 导入 PNG/JPG 建筑平面图；
* 设置地图比例尺；
* 绘制可通行区域和墙体；
* 点击添加出口、避难点、楼梯、门和小黑盒；
* 拖动调整小黑盒位置；
* 自动吸附到走廊中心线；
* 保存和加载工程；
* 导出 `boxes.json`、`exits.json` 和地图掩码。

这个版本不自动选点，但已经可以替代手工修改坐标文件。

## 2. 半自动布点编辑器

在基础编辑器上加入：

* 自动骨架化走廊；
* 自动识别路口、转弯和盲端；
* 自动生成强制布点；
* 长直走廊自动补点；
* 显示每个黑盒的探测半径和可视范围；
* 检测黑盒之间是否被墙体遮挡；
* 检查是否存在导航断链；
* 统计未覆盖区域；
* 自动给出修改建议。

这是当前项目最值得实现的版本。

## 3. 智能优化编辑器

后续可以增加：

* 在满足覆盖约束的前提下最小化黑盒数量；
* 关键区域双重覆盖；
* 任意一个黑盒失效后的 N-1 验证；
* LoRa 信号弱区标记；
* 自动比较多套布点方案；
* 根据成本、覆盖率和冗余程度给出评分。

# 三、前端技术方向

你们当前前端是 HTML5 与 ES6，可以直接采用 **Vanilla JavaScript + Konva.js**，不必强制迁移 React。

Konva 支持 Canvas 图形的拖拽、拖动事件、分层绘制和形状交互，适合在地图背景上编辑黑盒、出口、多边形和路径；其官方文档也提供了节点拖动和事件监听机制。([Konva.js][1])

建议将编辑器分为以下图层：

```text
Layer 1：原始建筑图片
Layer 2：墙体和可通行区域标注
Layer 3：走廊中心线和拓扑节点
Layer 4：出口、门、楼梯、避难点
Layer 5：黑盒候选点和最终部署点
Layer 6：探测范围、视线和覆盖热力图
Layer 7：路径链、错误标记和校验结果
```

编辑状态必须自己维护在 JSON 数据结构中，不能只把 Canvas 当作数据源。Konva 虽然支持 `toJSON()`，但其文档也建议在框架应用中保存独立的应用状态，而不是依赖画布对象本身序列化；事件处理器和图片等内容也不能完整序列化。([Konva.js][2])

推荐的前端状态：

```javascript
const editorState = {

    },

    polygons: {
        walkable: [],

    },

    }

```

# 五、自动提取中心线

后台接收编辑器生成的二值可通行掩码：

```text
0：墙体或不可通行区域
1：走廊或可通行区域
```

然后执行：

```python
from skimage.morphology import skeletonize

skeleton = skeletonize(walkable_mask)
```

骨架化可以将走廊区域压缩为内部的一像素宽中心线，适合后续提取拓扑节点。scikit-image 官方提供了 `skeletonize` 的标准实现和示例。([Scikit-image][3])

之后统计骨架点邻域：

```python
def classify_skeleton_point(x, y, skeleton):
    neighbors = get_skeleton_neighbors(x, y, skeleton)

    if len(neighbors) == 1:
        return "DEAD_END"

    if len(neighbors) >= 3:
        return "JUNCTION"

    if len(neighbors) == 2:
        if are_collinear(neighbors[0], (x, y), neighbors[1]):
            return "STRAIGHT"
        return "CORNER"

    return "ISOLATED"
```

自动布点时：

* `JUNCTION`：必须设置；
* `CORNER`：必须设置；
* `DEAD_END`：根据房间出口和盲端性质决定；
* `STRAIGHT`：超过最大间距时插值。

需要注意，骨架化结果可能存在毛刺和伪分支，因此必须加入：

* 短分支删除；
* 相近路口合并；
* 骨架平滑；
* 人工确认。

# 六、科学布点算法

## 1. 先生成候选点

候选点来源包括：

* 所有出口；
* 所有楼梯口；
* 所有交叉口；
* 所有转弯；
* 防火门两侧；
* 避难点入口；
* 长直走廊等距采样点；
* 高风险区域附近的附加点；
* 人工指定的强制点。

候选点不能直接全部变成实际黑盒，否则设备数量可能过多。

---

## 2. 建立覆盖矩阵

沿走廊中心线生成若干采样点：

$$
P={p_1,p_2,\ldots,p_n}
$$

黑盒候选点：

$$
C={c_1,c_2,\ldots,c_m}
$$

定义：

$$
A_{ij}=
\begin{cases}
1,&c_i能够覆盖并看见p_j\\
0,&否则
\end{cases}
$$

这里的“覆盖”不能只看欧氏距离，还必须满足：

```python
covered = (
    centerline_distance(box, point) <= max_distance
    and line_of_sight(box, point)
    and same_accessible_component(box, point)
)
```

隔墙的两个点即使距离很近，也不能判定为覆盖。

---

## 3. 使用硬约束

以下约束必须满足：

* 每个路口至少有一个黑盒；
* 每个转弯至少有一个黑盒；
* 每个出口入口处至少有一个黑盒；
* 任意连续走廊不能超过最大无指示距离；
* 黑盒必须在合法可安装区域；
* 相邻导航锚点之间必须存在可通行中心线路径；
* 路口前应能够提前看到指示；
* 路径链最终必须通向出口或避难点。

关键区域可以要求双覆盖：

$$
\sum_{i\in Cover(p_j)}x_i\geq 2
$$

普通区域要求：

$$
\sum_{i\in Cover(p_j)}x_i\geq 1
$$

---

## 4. MVP 使用贪心集合覆盖

当前不必直接使用复杂遗传算法。建议：

1. 先加入所有强制点；
2. 标记已经覆盖的走廊采样点；
3. 每次选择能够覆盖最多未覆盖区域的候选点；
4. 直到全部满足覆盖要求；
5. 尝试逐个删除非强制点；
6. 删除后仍满足所有约束则认定为冗余；
7. 最后允许人工调整。

伪代码：

```python
selected = set(mandatory_candidates)
uncovered = get_uncovered_samples(selected)

while uncovered:
    best = max(
        remaining_candidates,
        key=lambda c: weighted_new_coverage(c, uncovered)
    )

    selected.add(best)
    uncovered = get_uncovered_samples(selected)

for candidate in list(selected):
    if candidate.mandatory:
        continue

    trial = selected - {candidate}

    if satisfies_all_constraints(trial):
        selected = trial
```

这个方法具有：

* 结果稳定；
* 容易解释；
* 容易调试；
* 可以显示每个黑盒为什么被选中；
* 适合立项阶段和工程演示。

# 七、实时校验功能

编辑器的价值主要体现在校验，而不是单纯拖点。

## 1. 位置合法性

拖动黑盒时实时检查：

* 是否位于可通行区；
* 是否位于中心线附近；
* 是否落入墙体；
* 是否离墙过近；
* 是否与其他黑盒重叠；
* 是否超出安装区域。

非法位置显示红色，合法位置显示绿色。

## 2. 可见性检查

从黑盒到相邻黑盒或走廊采样点执行栅格射线检测：

```python
def has_line_of_sight(a, b, wall_mask):
    for x, y in rasterize_line(a, b):
        if wall_mask[y, x]:
            return False
    return True
```

转角处不能依赖一条穿墙视线。

## 3. 覆盖检查

显示：

* 绿色：至少被一个黑盒覆盖；
* 蓝色：关键区域双覆盖；
* 黄色：覆盖不足；
* 红色：完全没有覆盖。

## 4. 路径链检查

调用静态路径规划器，验证：

* 每个黑盒能否导向出口；
* 是否存在两个黑盒互相指向；
* 是否存在闭环；
* 是否存在断链；
* 箭头是否指向墙体；
* 黑盒间是否缺少可见锚点。

## 5. N-1 故障测试

依次模拟每个黑盒失效：

```text
删除 B001 → 检查导航链
恢复 B001
删除 B002 → 检查导航链
……
```

最终给出：

```text
总黑盒数量：58
单节点失效后仍保持完整导航：51
关键单点故障节点：7
建议新增冗余点：5
```

# 八、与火灾模拟联动

编辑器完成基础布点后，应提供“测试火源”模式。

用户可以：

* 点击地图放置火源；
* 设置火源强度；
* 设置烟雾扩散速度；
* 设置门开闭；
* 运行若干 Tick；
* 查看风险图；
* 查看哪些黑盒预警；
* 查看路径如何重新连接；
* 查看哪些区域进入 SOS。

这样编辑器不仅检查静态覆盖，还能检查：

* 火灾封锁某条走廊后是否存在替代链；
* 某个出口失效后是否能改道；
* 黑盒数量是否足以支撑动态重规划；
* 哪些区域容易成为导航孤岛。

建议在现有 FastAPI 后端中增加：

```text
POST /api/maps/import
POST /api/maps/compile
POST /api/maps/validate

POST /api/placement/candidates
POST /api/placement/optimize
POST /api/placement/validate

POST /api/simulation/fire
POST /api/simulation/run

GET  /api/maps/{map_id}
PUT  /api/maps/{map_id}
POST /api/maps/{map_id}/export
```

连续拖动黑盒时，不需要每个像素移动都调用后端。前端可以本地完成基本吸附和位置检查，在拖动结束后再请求完整拓扑验证。

WebSocket 可以用于传输自动布点结果、火灾模拟过程和动态校验结果。FastAPI 官方支持 WebSocket 连接、接收和发送持续消息，适合你们现有的实时地图展示架构。([FastAPI][4])

# 十一、推荐的首个可交付版本

第一版先完成以下闭环：

1. 上传平面图；
2. 设置比例尺；
3. 绘制墙体和可通行区；
4. 添加出口和避难点；
5. 自动提取中心线；
6. 自动生成转弯、路口和直线补点；
7. 拖动、删除和新增黑盒；
8. 显示覆盖半径；
9. 检查黑盒到出口的静态路径链；
10. 导出标准地图包。

先不要加入：

* 复杂 CAD/IFC 自动解析；
* 遗传算法；
* 自动识别所有建筑符号；
* 精确 LoRa 电磁传播模拟；
* 三维建筑编辑；
* 多人协同编辑。

先让编辑器能够稳定生成路径规划程序可直接读取的：

```text
map_meta.json
M_walkable.npy
M_wall.npy
M_fire_domain.npy
boxes.json
exits.json
refuges.json
doors.json
topology.json
```

这套地图盒布点编辑器完全可以实现，而且会显著提高整个项目的泛用性：路径算法不再与某张固定地图绑定，新地图只需要经过编辑器编译和校验，就能接入同一套火灾模拟与路径规划核心。
